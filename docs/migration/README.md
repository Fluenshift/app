# Migration records

Working records for the Prompt Evolution + Grifando merge. The process is defined in
[`MIGRATION_PROTOCOL.md`](./MIGRATION_PROTOCOL.md); the setup is in [`HANDOFF.md`](./HANDOFF.md).
Every JSON file in this directory is pure data. Prose about it lives here.

| Path | Contents |
| --- | --- |
| [`baselines.json`](./baselines.json) | The pinned source commits. |
| [`BASELINES.md`](./BASELINES.md) | Toolchains, run commands and recorded results for each baseline. |
| [`baseline-runs/<system>/`](./baseline-runs/) | Normalized test reports from the baselines, with a `manifest.json` per system. |
| [`inventory/<system>.json`](./inventory/) | Every source test case and normative clause, generated by `scripts/migration/inventory.ts`. |
| [`inventory/grifando-issues.json`](./inventory/grifando-issues.json) | Snapshot of Grifando's GitHub issues, an input of the inventory. |
| [`parity/<slice>.json`](./parity/) | The parity ledger: one row per inventory row, split by slice. |
| [`../../migration/characterization/<system>/`](../../migration/characterization/) | Characterization tests in each baseline's idiom (`files/`), and their reports (`reports/`). |

## `baselines.json`

One entry per source system, keyed by system name (`pe`, `grifando`). Each entry has exactly
three fields:

| Field | Meaning |
| --- | --- |
| `repository` | GitHub `owner/name` of the source repository. |
| `tag` | `parity-baseline`, or `parity-baseline-N` after a baseline bump. |
| `commit` | The full SHA the tag resolves to. This is the authority. |

Only the coordinator changes this file, in a baseline bump (`MIGRATION_PROTOCOL.md` §
Baseline bumps). `scripts/migration/baselines.ts` rejects any other field.

## `baseline-runs/<system>/manifest.json`

Written by `scripts/migration/baseline-run.ts`. One object:

| Field | Meaning |
| --- | --- |
| `system`, `repository`, `tag`, `commit` | The pin the run used. |
| `ranAt` | Start of the run, ISO 8601 UTC. Some baseline tests read the clock, so it matters. |
| `tools` | `name` and exact `version` of each tool on the run's `PATH`. |
| `services` | Containers the run started: `image`, its `digest` and the server `version`. |
| `install` | The install command. |
| `suites` | One entry per suite: `id`; `cwd`, relative to the baseline root; `runner` (`bun-junit`, `vitest-json` or `playwright-json`); `command` and extra `env`, with the report file name in place of its temporary path; `report`, the file next to the manifest; and `exitCode`. |

Paths inside the reports are relative to the suite's `cwd` for `bun-junit`, relative to the
baseline root for `vitest-json`, and relative to the Playwright `testDir` (itself
baseline-relative) for `playwright-json`.

## `inventory/<system>.json`

Generated, never edited by hand:

```bash
mise exec node@26.13.0 -- node scripts/migration/inventory.ts            # write both files
mise exec node@26.13.0 -- node scripts/migration/inventory.ts --check    # exit 1 unless reproduced byte for byte
```

The script reads only the pinned commit (git objects in the clone that `baselines.ts sync`
maintains), the stored reports in `baseline-runs/<system>/`, and, for Grifando, the issue
snapshot. It refuses reports whose manifest names another commit. Rows are sorted by `id`,
comparing digit runs as numbers and everything else by code unit, so the order does not
depend on the locale.

The file is one object: `system`, `repository`, `commit` (the pin) and `rows`. Every row has
`id`, `kind`, `source` and `title`; the other fields depend on the kind.

| `kind` | Rows | `id` | Other fields |
| --- | --- | --- | --- |
| `test` | Every test case as its runner reported it, so `.each` rows and skipped tests count the runner's way. | `<system>:test:<file>::<title>` | `suite`, the manifest suite; `baseline`, one of `green`, `baseline-red`, `skipped`, `todo` |
| `requirement` | PE: every FR and QR ID in `docs/product/REQUIREMENTS.md`. | `pe:requirement:<ID>` | `line`, `text` |
| `doc-rule` | PE: every paragraph, list item, table data row and code block of `RUBRIC.md` and `DATA-POLICY.md`, per section. | `pe:<rubric\|data-policy>:<section>:<nn>` | `line`, `text` |
| `smoke-check` | PE: every assertion in `scripts/docker-smoke.ts` `main()` and every shell check it runs in the container, titled by its `report()` phase. Grifando: every checklist item of `docs/deploy.md` §5. | `pe:docker-smoke:L<line>`, `grifando:deploy-smoke:<nn>` | `line`, `text` |
| `spec-section` | Grifando: every `##` and `###` section of `SPEC.md`, with its own body. | `grifando:spec:<number>` | `line`, `text` |
| `doc-bullet` | Grifando: every top-level bullet of `CLAUDE.md` under "Architecture rules" and "Public deployment model". | `grifando:claude-md:<section>:<nn>` | `line`, `text` |
| `fix-commit` | Grifando: every non-merge commit with a conventional `fix` subject, and every non-merge commit of a merged `fix/`, `hotfix/` or `bugfix/` branch. | `grifando:fix-commit:<short SHA>` | `commit`, `pullRequest` (the merged fix branch's PR, or `null`), `files` changed |
| `issue` | Grifando: every GitHub issue in the snapshot. | `grifando:issue:<number>` | `number`, `state`, `labels` |
| `characterization` | Every case of the characterization tests run at the baseline (`docs/migration/BASELINES.md`). Only green cases are accepted. | `<system>:characterization:<file>::<title>` | as `test` |

- `title`: for tests, the describe titles and the test title joined with ` > `; for clauses,
  the heading path, the ID, or the docker-smoke phase.
- `source`: the file at the pinned commit, relative to the source repository root; `git` for
  commits; `github` for issues.
- `line`: the clause's first line in `source`. `text`: the clause as written, with wrapped
  lines joined by single spaces; table cells joined with ` | `; code blocks verbatim.
- `baseline-red` is a test that failed in the stored run. It cannot serve as spec until the
  owners decide on its `needs-info` issue (listed in `BASELINES.md`).

`grifando-issues.json` was exported once, on 2026-11-13, with `gh issue list --repo
Fluenshift/grifando --state all` (number, title, state, labels, author, dates, URL, body and
comments, sorted by number). Refresh it only in a baseline bump.

## `parity/<slice>.json`

The ledger gives every inventory row a slice, a class, a disposition and, later, the target
tests that carry it in this repository. Each file is one object: `slice`, `lane`
(`evaluation`, `academy` or `platform`) and `rows`, sorted by `id` like the inventory.

| Field | Meaning |
| --- | --- |
| `id` | The inventory row's `id`. Every inventory row appears exactly once across all slices. |
| `source` | The inventory row's `source`, for reading convenience. |
| `class` | Test rows only: `A` ports nearly verbatim (pure code), `B` keeps its assertions on new persistence fixtures (SQLite or Postgres to PGlite), `C` is re-expressed as a contract test (SDK, Elysia, Next.js or Bun bound). `null` for other rows. |
| `slice` | The slice, also the file name. |
| `disposition` | `port`, `port-changed`, `superseded`, `drop`, `informative` or `pending-decision` (below). |
| `decision` | `adr:NNNN` (`docs/adr/NNNN-*.md`) or `issue:N` (a `needs-info` issue in this repo). Required for `pending-decision`, `port-changed`, `superseded` and `drop`; `null` otherwise. |
| `targets` | Target tests as `file::full title`, written by the unit that ports the row. A class C row also lists the source or characterization test it re-expresses. |

Dispositions:

- `port`: the behavior moves unchanged; for tests, the title stays verbatim and no assertion
  weakens (agent rule 3).
- `port-changed`: the behavior moves with the change an accepted ADR describes.
- `superseded`: replaced by other rows under an accepted ADR.
- `drop`: removed under an accepted ADR.
- `informative`: a non-normative clause with no behavior to port; a verifier confirms each.
- `pending-decision`: blocked by the open decision named in `decision`; nobody implements
  either side until it is settled (agent rule 7). Only these rows may have skipped tests.

The ledger stores no status. `scripts/migration/parity-check.ts` (gate G9) derives it from the
dispositions, the ADR index and the Vitest and Playwright reports:

| Status | Rows |
| --- | --- |
| `verified` | `port` and `port-changed` rows whose targets all pass |
| `open` | `port` and `port-changed` rows with no target yet |
| `blocked` | `pending-decision` rows |
| `terminal` | `superseded`, `drop` and `informative` rows |

```bash
mise exec node@26.13.0 pnpm@12.18.0 -- pnpm parity   # run every suite with JSON reports, then check
```

It fails when an inventory row is missing from the ledger or present twice, when a row is
malformed or not in the inventory, when a `port-changed`, `superseded` or `drop` row lacks an
accepted ADR, when a target is missing, failing, or skipped outside `pending-decision`, and
when a `port` target does not keep its source title. Without `--reports` it checks the
ledger's structure only.

Slices map to the protocol's phases and lanes:

| Slice | Lane | Phase | Contents |
| --- | --- | --- | --- |
| `evaluation-core` | evaluation | 3 | PE protected content, rubric, localization, model contract, calibration fixtures |
| `evaluation-persistence` | evaluation | 4b | PE writing evaluation, history, progress insights, database |
| `evaluation-judge` | evaluation | 4c | PE OpenRouter Judge |
| `evaluation-http` | evaluation | 4d | PE HTTP application, integration journey, dev proxy |
| `evaluation-web` | evaluation | 4e | PE web app |
| `evaluation-e2e` | evaluation | 4f | PE E2E journey and docker smoke |
| `evaluation-policy` | evaluation | 1 to 4 | PE requirements, rubric and data-policy clauses |
| `platform` | platform | 2 | Server configuration |
| `academy-core` | academy | 3 | Grifando pure domain: recall, mastery, difficulty, selection, streak, pattern keys, answers, analytics, prompt banks |
| `academy-trainer` | academy | 5c | Grifando AI prompts, schemas, providers, resilience |
| `academy-persistence` | academy | 5a, 5b, 5d | Grifando exercise, interview and writing services and repositories |
| `academy-http` | academy | 5e | Grifando API routes |
| `academy-web` | academy | 5e, 6 | Grifando browser code: highlights, landing specimen, Focus Music |
| `academy-spec` | academy | 1 to 6 | Grifando SPEC sections, CLAUDE.md bullets, fix commits, issues |
| `hosted` | platform | 6 | Sessions, rate limits, cleanup, BYOK, sitemap, deploy smoke |

`scripts/migration/ledger-seed.ts` wrote the first version from rules that a verifier can
review as a whole. It refuses to run once the ledger exists, because units then add targets;
`--force` reseeds and discards them.

Rows for inventory rows added later, such as new characterization cases, are added with
`scripts/migration/ledger-add.ts`: it appends `port` rows to one slice and never touches an
existing row.

`scripts/migration/parity-audit.ts` (gate G10) reads each class A and class B `port` row's
source test, at the pin or in `migration/characterization/`, and its target tests, and fails
when the targets make fewer `expect` or `assert` calls, drop a literal that a source matcher
expects, or check with a weaker matcher (`toBe` and `toStrictEqual`, then `toEqual`, then
`toMatchObject`; any other matcher by name). Class C rows are only reported. It needs the
baseline clones (`baselines.ts sync`); from a worktree, point `--root` at them:

```bash
mise exec node@26.13.0 -- node scripts/migration/parity-audit.ts --root ../app-baselines
```

## Issue labels

Work units and decision requests are GitHub Issues in this repository. State lives in labels,
never in files; a closed issue is done.

| Group | Labels |
| --- | --- |
| Status | `needs-triage`, `ready-for-agent`, `in-progress`, `in-review`, `needs-info`, `ready-for-human`, `wontfix` |
| Lane | `lane:evaluation`, `lane:academy`, `lane:platform` |
| Implementer | `implementer:claude`, `implementer:codex`, on the unit issue and its PR |
| Decision | `decision`: an owner decision request, including ADR acceptance |

## G12 verdict format

The verifier comes from the vendor that did not implement the unit. It posts one PR comment
that starts with exactly these three lines:

```text
G12 PASS
Verifier: codex
Head: <full head SHA>
```

The first line is `G12 PASS` or `G12 BLOCK`. `Verifier` names the verifying vendor (`claude`
or `codex`) and must differ from the PR's `implementer:` label. Reasons follow, and are
required for BLOCK. A verdict covers only that head SHA; any new commit needs a new verdict.

`scripts/migration/verdict-check.ts` computes the gate. The `G12 verdict` workflow runs it from
the default branch whenever a PR or its comments change, and sets the `G12` commit status on
the PR head: it passes only when the newest verdict for that head is `G12 PASS`, comes from an
organization member, and names a verifier other than the PR's `implementer:` label. The merge
queue admits only PRs whose `G12` status passed, so the workflow passes its merge group commit
as it is. To read a PR's verdict locally, without setting any status:

```bash
mise exec node@26.13.0 -- node scripts/migration/verdict-check.ts --repo Fluenshift/app --pr <number>
```

Until the workflow is on `main`, the coordinator checks verdicts by hand.

## Mechanical mapping

Changes allowed when a `port` row's test moves to the target stack. The title stays verbatim
and the assertions stay as they are.

| Source | Target |
| --- | --- |
| `bun:test` | `vitest` |
| `bun:test` matchers missing from Vitest: `toBeTrue()`, `toBeFalse()` | `toBe(true)`, `toBe(false)` (the same strict check) |
| `spyOn` | `vi.spyOn` |
| `import.meta.dir` | `import.meta.dirname` |
| `Bun.env` | Effect Config |
| SQLite temporary files | PGlite |
| Elysia `app.handle`, Next.js route handlers | Hono `app.request` |
| Prisma enums | literals from `packages/contract` |
| SDK fakes (openai, Anthropic, Gemini) | AI SDK mock models |
| `Buffer` byte inputs in tests of `packages/core` and `packages/contract` | the same bytes as `Uint8Array` (`new TextEncoder().encode(...)`) |
| A sequential `await` in a test loop, which lint rejects | `Promise.all` over the same cases, followed by the same assertions |
| Zod `schema.safeParse(input)`, read through `.success` and `.data` | a test helper `safeParse(schema, input)` over `Schema.decodeUnknownOption`, returning the same two fields |
